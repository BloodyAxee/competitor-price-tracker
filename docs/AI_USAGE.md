# Использование ИИ при разработке

## Роль

OpenAI Codex использовался как инструмент разработки и исследования. ИИ не входит в runtime решения, приложение не обращается к OpenAI API, ключ OpenAI не требуется и в репозитории отсутствует.

Конкретное имя внутренней версии модели не закреплено в коде, чтобы журнал не создавал ложную техническую зависимость. Для сложных архитектурных и исследовательских задач использовался reasoning-режим Codex семейства GPT, для проверок применялись обычные тесты и воспроизводимые команды.

## Для чего использовался Codex

| Область | Работа ИИ | Обязательная проверка |
| --- | --- | --- |
| План | разбиение ТЗ на этапы, риски и критерии готовности | сверка с исходным ТЗ и ответами руководителя |
| Архитектура | схема PostgreSQL, API, worker, web и Docker Compose | миграции с пустой базы, build и smoke-тесты |
| Код | реализация и рефакторинг адаптеров, API и интерфейса | unit, integration, live smoke и ручной просмотр |
| Исследование | поиск карточек, сопоставление маркировок и характеристик | URL, дата, критичные признаки и реальный сбор |
| Тесты | fixtures, отрицательные случаи и acceptance script | запуск в Python 3.13, Node 24 и контейнерах |
| Документация | план, аудит, ограничения, вопросы и сценарий демо | сверка с фактической базой и последним job |

## Основные классы запросов

- проанализировать требования и предложить последовательный план на выбранном стеке
- создать PostgreSQL 18 схему с append-only историей и forward-only миграциями
- реализовать сбор с таймаутом, ограниченным повтором, нарастающей паузой и изоляцией ошибок
- не допускать похожую модель или конфликтующую комплектацию в итоговое сравнение
- проверить конкретные карточки конкурентов и найти независимые точные источники
- сохранить сомнительные карточки для маркетолога, не подмешивая их цену в итог
- упростить интерфейс для ежедневной работы маркетолога
- проверить чистый запуск, сохранность истории, CSV, расписание и частичный успех

Полные пользовательские сообщения не копируются в репозиторий, поскольку они содержат рабочий контекст и могут включать данные интерфейса. Здесь сохраняется достаточный для аудита смысл запросов.

## Что ИИ не решал самостоятельно

- не подтверждал официальное дилерство только по заявлению самого сайта
- не решал CAPTCHA автоматически. Реализовал ограниченный браузерный повтор, сохранение сессии и явный переход к проверке человеком
- не повышал карточку до exact только по одинаковому названию
- не утверждал спорные параметры без первичного документа
- не выбирал за руководителя правила будущих комплектов
- не выполнял push в GitHub

## Контроль ошибок ИИ

Каждый источник проходит машинное правило идентичности и критичных характеристик. Live-сайт используется только как smoke-test, а CI-устойчивые проверки основаны на fixtures. Все изменения фиксируются отдельными Git-коммитами. Секреты проверяются перед коммитом, реальный `.env` не отслеживается Git.

Пять спорных моделей оставлены в review именно потому, что публичных данных недостаточно для надёжного решения. Это важнее формального 100-процентного покрытия.
